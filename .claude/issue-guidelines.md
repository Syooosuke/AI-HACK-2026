# Issue の書き方（このリポジトリの決まり）

Issue は**着手する人が課題を理解しながら進められる状態**で書く。
「何をやるか」だけでなく、**なぜ必要か・いまどうなっているか・どこを触るか**を必ず含める。

保守や不具合修正に限らず、**新機能の提案も Issue にする**。

---

## 必ず入れる6つの欄

以下の見出しをこの順で使う。空欄にしない（該当が無ければ「特になし」と書く）。

```markdown
## 背景
なぜこれをやるのか。誰がどう困っているか、あるいは何が価値になるか。
仕様（`spotcheck-ai/CLAUDE.md` / `spotcheck-ai/docs/`）との関係もここに書く。

## As-Is（現状）
**いま実際にどう動いているか。** コードを読んだ結果に基づいて書く。
「未実装」「プレースホルダのまま」「〜のとき失敗する」など、事実を具体的に。

## To-Be（あるべき姿）
完了したとき何ができるようになるか。**受け入れ条件を箇条書き**にする。
画面の変更なら、どの画面のどこがどうなるかまで書く。

## 懸念事項
先に潰しておくべき論点。判断が必要なこと、壊しやすい箇所、性能・費用・法令・
プライバシーへの影響。**「ここは人間に確認すべき」も明記する。**

## 作業内容
着手順に並べた作業のチェックリスト。バックエンド／フロントエンド／ドキュメント／
テストで分けると迷いにくい。

## 関連コード
触ることになるファイルを**行番号付きで**挙げ、それぞれ何をしている場所か1行で説明する。
`backend/app/services/xxx.py:42` の形式で書くとエディタから飛べる。
```

---

## 書くときの原則

| 原則 | 理由 |
|---|---|
| **As-Is は実際のコードを読んで書く** | 推測で書くと着手者が二度調べることになる |
| **関連コードは行番号まで示す** | 探す時間をゼロにする。着手の心理的障壁が一番下がる |
| **受け入れ条件は検証できる形にする** | 「使いやすくする」ではなく「タップで消える」と書く |
| **懸念事項に判断待ちを書く** | 勝手に決められると手戻りになる。`CLAUDE.md` 3節の「人間に確認すべきケース」に該当するものは必ず書く |
| **1 Issue = 1 PR で終わる大きさにする** | 大きすぎるものは親Issueに分割して子Issueを列挙する |
| **既存の設計判断（D-01〜D-10）に反する提案は理由を書く** | `CLAUDE.md` 2節は勝手に変えられない |

---

## ラベル

| ラベル | 使うとき |
|---|---|
| `enhancement` | 新機能・改善 |
| `bug` | 期待どおり動かない |
| `documentation` | ドキュメントのみ |
| `good first issue` | 触る範囲が狭く、仕様理解が浅くても進められる |
| `help wanted` | 判断や知見が必要で、着手者を募りたい |

---

## テンプレート

`.github/ISSUE_TEMPLATE/task.md` に同じ構成のテンプレートを置いてある。
GitHub の画面から Issue を作ると自動で読み込まれる。

`gh` から作る場合は本文を直接渡す。

```bash
gh issue create --title "..." --label enhancement --body "$(cat <<'EOF'
## 背景
...
EOF
)"
```

# AI HACK 2026 想定問答集（SpotCheck AI）

最終プレゼン **4分＋質疑応答3分**、およびブース審査で審査員から聞かれうる質問と回答の準備。
審査基準（1. 課題の実在性 / 2. ビジネス成立性 / 3. 完成度・デモの説得力 / 4. AIである必然性 /
5. 技術的な作り込み / 6. LLMコスト / 7. セキュリティ / 8. 次世代性・独創性）に対応させている。

**回答の作り方**
- 質疑は1問あたり **30〜45秒**。まず結論、次に根拠となる数字、最後に限界を1文。
- **限界を先に自分から言う。** 実測して分かった失敗を隠すと、次の質問で崩れる。
- 数字は 13節のチートシートから引く。うろ覚えの数字を言わない。

## 0. 30秒の基本形（どの質問でも土台になる説明）

> SpotCheck AI は、遠隔地の「今」を確認したい依頼者と、その場所の近くにいるワーカーをつなぐ
> プラットフォームです。特徴は **人間による目視検品を一切置いていない**ことで、
> ①依頼文の安全性・十分性の審査、②提出画像が依頼条件を満たすかのVLM検品、
> ③位置偽装の検知、④顔・ナンバープレートの自動マスキング までをAIが通しで処理します。
> 依頼作成から加工済み画像の納品までが、人の介在なしに完結します。

**3つの数字で補強する**
- AI呼び出しの監査ログ `ai_invocations` に purpose / model / latency / usage を全件記録している
- バックエンドテスト **294件**（`pytest --collect-only` 時点）
- 依頼審査は実測 **正当14/14・悪意8/8**、画像検品は **5/5・合格側の余裕 +18点**

## 1. 課題の実在性

### Q1-1. その課題は本当に存在しますか？ 自分で確認しに行けばよいのでは？

**回答**
検索・地図・生成AIで得られるのは、**過去に公開された情報**です。行列の長さ、営業しているか、
工事や設備が今どうなっているか、といった「特定地点の今」には届きません。確実に知るには現地へ
行くしかありませんが、遠方であれば確認1回のために移動時間と交通費がかかります。
ライブカメラは設置地点と画角が固定です。SpotCheck は「今そこにいる人」に代わりに見てもらう、
という形でこの穴を埋めます。

**深掘りされたら**
想定用途は不動産の空室・外観確認、屋外広告の掲出監査、工事の進捗確認、店舗の混雑確認、
災害後の周辺状況。いずれも**現在も人が現地へ行って確認している**業務で、需要そのものは
既存の外注・巡回として存在しています。私たちが変えているのは「誰が行くか」と「誰が検品するか」です。

### Q1-2. 既存サービスで足りているのでは？（Pic4Pay / PhotoTask / Field Agent など）

**回答**
現地写真のマッチング（Pic4Pay、PhotoTask）と、撮影後のAI解析（homepic AI など点検アプリ）は
それぞれ存在します。**今回調べた公開情報の範囲では、依頼審査→撮影→AI検品→再撮影指示→
マスキングまでを一気通貫で自動化しているサービスは確認できませんでした。**
私たちの独自性は個々の技術ではなく、**マーケットプレイスとAIパイプラインを1つのワークフローに
接続した点**にあります。詳細は `docs/competitor-research.md` に調査日付き（2026-08-14）で残しています。

> **言い方の注意**：「競合にはAIがない」「世界初」「唯一」とは言わない。
> 「公開情報で確認できなかった」と限定する。

## 2. ビジネス成立性

### Q2-1. どう収益化しますか？

**回答**
依頼者からの支払い額とワーカーへの報酬の差分（テイクレート）を想定しています。報酬は
1人あたり100〜100,000円の範囲で依頼者が設定し、撮影人数 N を指定できます。
**現時点で決済は意図的にスタブです**（設計判断 D-03）。`payments` テーブルに charge / payout を
1件ずつ記録し、外部決済SDKは入れていません。9日間でAIパイプラインの実装を優先したためで、
収益化そのものの実証はまだできていません。ここは正直に未達です。

### Q2-2. AI検品で人件費が浮くと言うが、それがビジネス上どう効きますか？

**回答**
**単価の低いロングテール依頼が成立するようになります。** 1件2,000円の撮影依頼に対して
人が目視検品すると、検品コストで粗利が消えます。検品を自動化すると、
「行列の写真1枚」のような小さな依頼でもユニットエコノミクスが立ちます。
加えて、検品が**ワーカー単位で逐次**走るため（D-07）、N人依頼でも全員の完了を待たずに
合格した人から納品・報酬確定でき、資金の回転が早くなります。

### Q2-3. ビジネス上、最大の問題は何だと思っていますか？（自分から出す）

**回答（正直に）**
4つあります。

| 問題 | 内容 |
|---|---|
| **二面市場のコールドスタート** | 依頼が来る地点にワーカーがいなければ成立しない。地理的密度が命で、全国同時展開は無理。初期は都市部＋特定業種（不動産管理・広告監査）に絞る必要がある |
| **法務の責任分界が未整備** | 撮影行為の適法性（私有地・肖像権・施設管理権）で問題が起きたとき、AIが承認した依頼の責任を誰が負うのか。利用規約と保険が無い |
| **AI誤判定の事業コスト** | 誤却下は依頼者の失注、誤失格はワーカーの離脱に直結する。現状**異議申し立てのフローが無い** |
| **LLMコストが売上原価に乗る** | 1依頼あたり概ね8〜14回の推論呼び出しが発生する（6節）。低単価依頼では粗利を直接圧迫するため、モデル選定がそのままユニットエコノミクスになる |

**参入障壁についての正直な認識**：AI機能そのものは競合が後付けできます。堀になるのは
マッチングの地理的密度と、プロンプト・しきい値・失敗事例の蓄積（11節）です。

### Q2-4. ワーカーは集まりますか？

**回答**
通勤・買い物のついでに1枚撮る、という低い参加コストを想定しています。ただし
**移動してまで撮る動機が出る報酬額**と、**依頼者が払える上限**の間は狭く、ここは実データで
検証していません。現状は `min_worker_rating` による受注条件と、評価・信頼度スコアで
質を担保する仕組みまでを実装した段階です。

## 3. 完成度・デモの説得力

### Q3-1. どこまで動きますか？

**回答**
**Phase 0〜7 が完了しており、本番URLで一気通貫が動きます。**
Cloud Run にデプロイ済みで、スマートフォンの実機（HTTPS）でカメラとGPSが動作します。
`main` への push を GitHub Actions が検知し、DBマイグレーション→バックエンド→フロントエンド→
疎通確認 の順で自動デプロイします。疎通確認まで通らなければ成功扱いにならず、失敗時は
Cloud Run が直前のリビジョンで動き続けます。

- 実装画面：①依頼作成 〜 ⑩結果詳細 ＋ ⑪公開プロフィール
- バックエンドテスト：**294件**
- 実機確認：ログイン、投稿一覧、地図検索、ストリートビュー、カメラ撮影、通知

### Q3-2. デモ中に外部APIが落ちたらどうしますか？

**回答**
`ORCA_STUB_MODE=true` にすると **HTTP通信を一切行わず固定レスポンスで全画面が通ります**。
これは最初から必須要件として維持している仕様です。スタブ応答も実呼び出しと同じエンベロープに
包むため、解析経路は共通です。Google Maps のキーが失敗した場合も `window.gm_authFailure` で
検知して緯度経度の手入力へ切り替わり、Street View が取れない地点はサーバー描画の
プレースホルダ画像へ落ちます。

**深掘りされたら**：スタブは検品の `attempt_no` が奇数なら不合格、偶数なら合格を返します。
**デモで再撮影ループを必ず1回見せるため**の意図的な挙動です。さらに、スタブが画像を見られない
ことによる破綻を2点潰しています——不合格理由に「暗すぎます」を使わない（夜間撮影で嘘だとバレる）、
`daylight_state` を申告撮影時刻から決める（固定値だと環境整合チェックが誤作動する）。

### Q3-3. スタブモードだと安全審査が素通りするのでは？

**回答**
そのとおりです。**だから決定論フィルタ（`content_filter.py`）をLLMの前段に置いています。**
盗撮・のぞき見・空き巣・侵入経路といった単語の単独一致と、「施錠×侵入」のような2語の共起で
LLMを呼ばずに `rejected` を確定します。NFKC正規化して空白を除くため「盗 撮」「ｽﾄｰｶｰ」も弾きます。
スタブモードではこれが唯一の防波堤になります。

## 4. AIである必然性

### Q4-1. ルールベースでできることをAIでやっていませんか？

**回答**
**逆に、ルールでできることは意図的にルールでやっています。** 使い分けは明確です。

| 判定 | 手段 | 理由 |
|---|---|---|
| 明白な犯罪目的の依頼 | **キーワードの決定論フィルタ** | LLMは指示を無視することがある。取り返しのつかない却下漏れを防ぐ多層防御 |
| 位置の整合（距離・時刻・精度） | **Haversine距離などの計算** | 数値比較で確定できるものをLLMに投げる理由がない |
| 依頼文の意図と十分性 | **LLM** | 文脈依存。「所有物件の施錠部分の破損確認」と「隣人が留守の時間に忍び込めそうな場所」は語彙が重なる |
| 提出画像が依頼条件を満たすか | **VLM** | 依頼ごとに条件が違う。事前定義した項目のチェックでは表現できない |
| 顔・車両の検出 | **ローカルYOLO** | 定型の物体検出。外部LLMに投げるのは無駄 |
| ナンバープレート・表札の座標 | **VLM** | 軽量な物体検出モデルでは精度が出ない |

### Q4-2. 「依頼ごとに条件が違うからVLMが要る」の具体例は？

**回答**
店舗棚調査サービスは撮影項目が固定なので、専用の画像解析で高精度が出ます。SpotCheck は
用途を固定しません。「駅前の再開発工事の全景と仮囲いの位置」と「テナント募集中かどうか分かる
入口の様子」では、合格条件がまったく違います。**自由記述の依頼文を、その場で判定基準へ
変換できる**のがVLMを使う理由です。合格・不合格を返すだけでなく、
「街灯の下に寄り、対象を明るく写してください」のような**次の行動が分かる30文字以内の再撮影指示**を
日本語で生成させ、ワーカーの画面に返しています。

### Q4-3. 決定論フィルタの精度で失敗した経験はありますか？（実測の話ができる）

**回答**
あります。共起ルールの意図側に「確認」「状況」「把握」「撮影」「様子」を置いていた時期があり、
これらは撮影依頼なら必ず出る語なので、実質**対象語1つで弾くのと同じ**になっていました。結果：

- 「マンション共用部の防犯カメラの設置状況」→ **誤って却下**
- 「隣人が留守の時間に裏口へ回り込み、忍び込めそうな場所を」→ **素通り**

意図側には「侵入」「死角」「解錠方法」「窃盗」など**それ自体が加害を示す語だけ**を残しました。
方針は「**誤検知を抑える側を優先し、迷うものはAI審査に委ねる**」です。
「自宅の外壁のひび割れを撮ってほしい」を止める方が、サービスとしては痛いからです。

## 5. 技術的な作り込み

### Q5-1. AIの出力が安定しない問題にどう対処しましたか？

**回答**
これが一番作り込んだところです。**同じ画像・同じプロンプト・`temperature=0.2` でも、
スコアが 30 と 95 のように合否をまたいで振れる**ことを実測しました。決定性はパラメータでは
買えないので、4層で対処しています。

1. **`response_format` でJSONの形をAPIに強制する**（プロンプトで「JSONだけ返して」と頼むのをやめた）
2. **Pydanticでバリデート**し、失敗したら直前の出力を見せて再試行
3. **重要な判定は多数決**——依頼審査は主モデル＋合議2つの**3票**を並行実行
4. **画像検品は境界だけ厚くする**——`|score − しきい値| ≤ 15` のときだけ追加モデルへ問い合わせる

**なぜ全件を3回呼ばないのか**：振れるのは境界付近だけで、明らかな合格・不合格は2回とも一致
しました。待っているのは現地のワーカーなので、待ち時間を一律3倍にする価値はありません。

**なぜ合議を2モデルで組まないのか**：2モデルで意見が割れると必ず同数になり、
タイブレーク規則（`rejected > needs_info > approved`）で常に却下へ倒れるからです。

### Q5-2. `response_format` で具体的に何にハマりましたか？

**回答**
Pydantic の `model_json_schema()` をそのまま渡すと**アップストリームごとに 400 が返り、
400 はリトライされないのでその用途が丸ごと落ちます。**

| アップストリーム | 400 の理由 |
|---|---|
| Anthropic 系 | `object` に `additionalProperties: false` が明示されていない |
| Gemini 系 | `$defs` / `$ref` を解釈できない |

`_normalize_schema()` で `$ref` を実体へ展開し、全 `object` に `additionalProperties: false` を
付けて両方の制約を満たすようにしました。

### Q5-3. モデルはどう選びましたか？「最新の高性能モデルを使いました」ではないですよね？

**回答**
**分類軸は「画像の有無」ではなく「間違えたときの損失」**です。

| 段階 | 間違えると何が起きるか | 用途 |
|---|---|---|
| S: 取り返しがつかない | 犯罪の幇助・不当な失格・個人情報の公開 | 依頼審査 / 画像検品 / マスキング座標 |
| A: 品質に響くが回復可能 | 納品文が的外れ | 調査結果の総括 |
| B: やり直しが効く | 見た目が少し悪い | 詳細メッセージ生成 / サムネイル情景説明 |

選定は実測ベンチ（`scripts/bench_task_review.py` 正当14件＋悪意8件、`scripts/bench_models.py` 実写真）で
決めました。**正答率だけでは選びません。** `claude-haiku-4.5` は画像検品で5/5正答でしたが、
合格すべき写真のスコアが 72〜75 で、当時のしきい値70に対し**わずか+2**しかありませんでした。
振れ幅を考えると、まともな写真が再撮影になります。**合格側の余裕（min(合格スコア) − しきい値）**を
併せて見て、余裕 +18 の `claude-opus-5` を採用しています。

### Q5-4. ルーターの `auto` を使わないのはなぜですか？（スポンサーへの配慮も込みで）

**回答**
OrcaRouter は**用途ごとのモデル差し替えを環境変数だけでできる**のが大きな利点で、
`OrcaClient` に呼び出しを集約したことで業務ロジックを一切書き換えずにモデルを変更できます。
そのうえで、`orcarouter/auto` は**重要な用途には使わない**という判断をしました。理由は実測です。

- 同じプロンプトで `qwen3.7-plus` と `deepseek-v4-pro` の両方に振られるのを観測した
- 推論モデルへ当たると reasoning tokens だけで `max_tokens` を使い切り、`finish_reason="length"` で
  **本文が空**のまま返る。依頼文生成（当時 `max_tokens=300`）で **8件中7件がこれで失敗**
- 品質が落ちても気づけない

そこで tier の既定にも具体的なモデルを置き（light に `gpt-5.4-mini`：実測1.4秒・8/8成功、
vision に `qwen3-vl-235b`：Vision非対応へ振られる事故が起きない）、用途ごとに明示指定しています。
**モデル名はコードに1つも書いていません。**環境変数のみです。

### Q5-5. 検品プロンプトのチューニングで何を学びましたか？

**回答**
**合格の基準は「きれいに撮れているか」ではなく「依頼者が判断できるか」**だと分かりました。
当初の配点（対象40 / 構図20 / ピント20 / 明るさ20）では**構図と写りの良さで60点**を占め、
対象が写っていても粗ければ落ちます。実測でブレた写真が72点（当時のしきい値70に対し+2）で
境界に張り付いていました。現地で1枚撮るだけのワーカーには達成困難で、再撮影上限（2回）を
超えると受注そのものが取り消されます。

配点を「**対象が写っている60 / 状態が読み取れる25 / 構図10 / 明るさ5**」へ組み替え、
傾き・端寄り・軽いブレ・暗さを減点理由から外しました。

| | 変更前 | 変更後 |
|---|---|---|
| 合格すべき7ケースの最低score | 72（しきい値70 / 余裕 **+2**） | 76（しきい値60 / 余裕 **+16**） |
| 不合格にすべき2ケース | 10 | 20（しきい値との差 −40） |
| 粗い写真に付いた issues | `TOO_BLURRY` | なし |

**緩めていないもの**：対象の有無（`subject_present`）と、位置・時刻の検証。
`subject_present == false` はスコアに関わらず不合格です。

### Q5-6. 依頼審査プロンプトでも同じような失敗はありましたか？

**回答**
より深刻な失敗をしました。当初「〜と**解釈できる**もの」で fail を定義していたところ、
**実測した6モデルすべてが正当な依頼の6〜8割を却下**しました（`orcarouter/auto` で 3/14、
`gpt-5.4-mini` で 4/14 しか承認されない）。「所有物件の玄関ドアの施錠部分の破損確認」まで
「侵入の下見と解釈できる」として落ちます。**モデルを変えても直りません。**

fail の条件を「**依頼文から意図が読み取れる場合に限る**」へ変え、pass にすべき例を明示しました。
プロンプトに「却下された依頼は書き直して再申請できません。正当な依頼を1件却下する損失は、
判断に迷う依頼を1件通す損失より大きい」と非対称性を明記しています。

### Q5-7. 位置偽装（Spoofing）はどう検知していますか？

**回答**
**LLM任せにせず、まず決定論的な計算を行います。** 6項目です。

| # | チェック | 影響 |
|---|---|---|
| C-1 | 依頼地点と撮影座標の Haversine 距離 > 100m | **合否に直結** |
| C-2 | 申告撮影時刻とサーバー受信時刻の差 > 300秒 | **合否に直結** |
| C-3 | 撮影希望日時とのズレ > ±6時間 | 減点 −5 |
| C-4 | EXIF GPS と申告座標の距離 > 200m | 減点 −20 |
| C-5 | VLMが読んだ画像の光の状態と撮影時刻の矛盾 | 減点 −20 |
| C-6 | Geolocation の精度 > 500m | 減点 −5 |

これを合成した `reality_score`（0〜100）を依頼者に見せます。加えてAPI層で
**撮影から送信まで10分（`CAPTURE_FRESHNESS_SECONDS`）**を超える提出を同期的に弾き、
撮り置き画像の投稿を防ぎます。

**限界も先に言う**：GPS座標は端末が申告する値なので、**偽装を完全には防げません。**
私たちがやっているのは、画像の環境整合・EXIF・鮮度・距離を重ねて**偽装のコストを上げる**ことです。
C-5 の日出没判定も「6時〜18時を daylight」の簡易判定で、季節と緯度を考慮していません
（`method: "simple_hour_range_6_18"` として記録に残しています）。

### Q5-8. EXIF に GPS が無い画像はどう扱いますか？

**回答**
**GPSが無いこと自体は不合格にしません。** ブラウザの `getUserMedia` で撮影した画像には
EXIF GPS が入らないためです。だからこそ設計判断 D-02 で、**画像・デバイス位置情報・撮影時刻を
同一リクエストで送る**方式にし、EXIFは「あれば照合する」補助検証に位置づけています。
EXIFの撮影時刻もタイムゾーン情報が無いため、合否判定には使わず参考表示のみです。

### Q5-9. マスキングをクラウドVision APIでなくローカルYOLOにしたのはなぜ？

**回答**
3つあります。①**画像の原本を外部サービスへ渡さない**——プライバシー保護のための処理で
原本を外に出したら本末転倒です。②**1枚あたりの外部課金がゼロ**になる。③レイテンシ。
2モデル構成で、汎用モデル（`yolov8n.pt`）が person / car / truck / bus / motorcycle を、
顔モデル（`yolov8n-face.pt`）が顔を直接検出します。汎用モデルの推論は1回だけ行い、
結果を人物と車両へ振り分けます。

**処理の使い分けにも意図があります。**

| 対象 | 検出 | 処理 |
|---|---|---|
| 通行人の顔 | ローカルYOLO | ぼかし（矩形を上下左右に10%拡張） |
| 人物全体 | YOLO | **ぼかさない**（工事状況の確認に必要）。検出数だけ記録 |
| 車両 | YOLO | ぼかさない。**プレート探索のヒント**としてVLMへ座標を渡す |
| ナンバープレート | VLM座標 | **黒塗り**（完全マスク） |
| 表札・番地・書類 | VLM座標 | ぼかし |

プレートと表札は軽量な検出モデルでは精度が出ないため、VLMに正規化座標（0〜1）で返させ、
確信度0.3未満と不正な座標（`x2<=x1` 等）は採用しません。
**重みが無い環境でも例外を出さず、VLM座標だけで続行**して警告ログを残します。

### Q5-10. 技術的に一番地味だが効いた対処は？

**回答**
Supabase の transaction pooler（PgBouncer）経由で、psycopg3 の
**サーバー側プリペアドステートメントを無効化**したことです（`prepare_threshold=None`）。
psycopg3 は同じSQLを5回実行するとプリペアドへ切り替えるため、
**最初の数回は成功し、その後だけ `prepared statement "_pg3_1" does not exist` で失敗する**という
非常に分かりにくい壊れ方をします。本番でしか出ない類の障害です。

## 6. LLMコスト

### Q6-1. 1件あたりのLLMコストをどう見積もっていますか？

**回答**
**呼び出し回数と入力サイズの両方を設計で抑えています。** 呼び出し回数の内訳は次のとおりです。

| 場面 | 呼び出し | 回数 |
|---|---|---|
| 依頼文の下書き生成（任意） | light tier（`gpt-5.4-mini`） | 0〜1 |
| 決定論フィルタで却下 | **LLMを呼ばない** | **0** |
| 依頼審査 | 主モデル＋合議2（並行） | 3 |
| サムネイル生成 | VLM情景説明＋画像生成 | 0〜2 |
| 画像検品（提出1回） | VLM。境界に入ったときだけ +2 | 1〜3 |
| マスキング座標（合格時のみ） | VLM | 0〜1 |
| 調査結果の総括（合格時のみ） | VLM | 0〜1 |

**1依頼が「1人・再撮影1回で完結」する場合、概ね 8〜14 回**です。
実額はモデル単価に依存するため断定しませんが、**`ai_invocations` テーブルに全呼び出しの
`usage`（prompt / completion / total tokens）とモデル名・レイテンシを記録している**ので、
実測での原価計算が可能な状態にしてあります。

### Q6-2. コストのためにどんな具体策を取りましたか？

**回答**

| 施策 | 効果 |
|---|---|
| **決定論フィルタを前段に置く** | 明白に黒い依頼はLLMを呼ばずに却下。呼び出し自体が発生しない |
| **用途 × リスクでモデルを分ける** | 飾り（サムネイル情景説明・依頼文生成）に高価なモデルを使わない |
| **合議は依頼審査のみ常時、検品は境界だけ** | 全件3倍にせず、振れる領域にだけコストを払う |
| **画像を長辺1568pxへ縮小しJPEG品質85で再エンコード** | 入力トークンを削減。bboxは正規化座標なので縮小しても解釈は変わらない |
| **`max_tokens` を用途別に設定** | 既定4000、マスキング座標は800。`finish_reason="length"` を検出したときだけ倍化（上限8000） |
| **`ORCA_STUB_MODE=true`** | デモ・開発時の課金をゼロにできる |
| **ベンチをCIに入れない** | 実モデル比較は課金が発生するため、モデル・プロンプト変更時に手動で流す |

### Q6-3. 合議で3倍のコストを払う価値はありますか？

**回答**
**依頼審査だけは払う価値があると判断しました。** 誤判定の損失が非対称だからです。
`rejected` は行き止まりで、依頼者は書き直して再申請できません（`resubmit` は `needs_info` の
依頼しか受け付けない）。誤った却下はそのまま失注になります。

一方**画像検品は全件多数決にしていません。** 明らかな合格・不合格は2回とも判定が一致し、
振れるのは境界付近だけだったからです。現地でワーカーが待っているので、待ち時間を一律3倍に
する価値はないと判断し、`|score − しきい値| ≤ 15` のときだけ追加判定します。
**コストと待ち時間と精度のトレードオフを、判定の種類ごとに変えている**のが要点です。

### Q6-4. モデルを安いものに変えたくなったらどうしますか？

**回答**
環境変数を1つ変えるだけです。`ORCA_MODEL_TASK_REVIEW` など6つの用途別変数と、
`ORCA_ROUTER_LIGHT` / `ORCA_ROUTER_VISION` の tier 既定で決まります。**コード変更は不要です。**
ただし変えたら必ず `bench_models.py` と `bench_task_review.py` を流します。
「気づいたら精度が落ちていた」を防げるのは実測だけなので。
`bench_task_review` で見るべき指標は**誤却下（正当な依頼を却下した数）**です。

なお、デプロイ側ではモデル割り当てを GitHub の **Secrets ではなく Variables** に置いています。
秘密情報ではないうえ、「いつからどのモデルに切り替えたか」の履歴が事故調査で効くためです。

## 7. セキュリティ

### Q7-1. 個人情報はどう守っていますか？

**回答**
最重要の不変条件は「**マスキング前の原本を、クライアントにもワーカー本人にも絶対に返さない**」ことです。
4層で守っています。

1. **バケットを分離**（`submissions-raw` / `submissions-processed`。どちらも非公開）
2. **APIレスポンスに `raw_image_url` を一切含めない**
3. ローカルストレージ運用時の配信 `/api/files/{bucket}/{key}` は、
   **bucket が加工済みバケットでなければ 403**（URLを推測されても原本は出ない）
4. **テストで機械的に検証**（`test_submission_pipeline.py` の原本URL非露出、`test_files_route.py` の原本バケット配信拒否）

原本は削除せず raw バケットに残します。**争議時の証跡**として必要だからです。
配信URLは有効期限1時間の署名付きURLです。

### Q7-2. AIの監査ログに画像や個人情報が残りませんか？

**回答**
`ai_invocations` には全呼び出しを記録しますが、**画像のbase64は保存せず、URLまたは
`"<image omitted>"` に置換**しています。記録は独立セッションでコミットするため、
業務トランザクションがロールバックしても監査ログだけは残り、逆に記録に失敗しても本処理は止まりません。

**限界**：依頼文そのものはプロンプトとして `request_payload` に残ります。依頼文に個人情報が
含まれうるため、本番運用ではここへのアクセス制御と保持期間のポリシーが必要です。現状は未整備です。

### Q7-3. 認証・認可はどうなっていますか？

**回答**
ログインID＋パスワードで、パスワードは bcrypt ハッシュ、トークンは JWT（HS256・既定30日）です。
`Authorization: Bearer` で受け取り、`app/api/deps.py` の `get_current_user()` が唯一の入口です。

**設計上の特徴として、users に role を持たせていません**（D-06）。1アカウントで「依頼する」と
「撮影する」の両方を行うためで、権限は**依頼のオーナーか、その依頼の受注者か**で判定します。
ロールによる出し分けが無いぶん、認可の判定箇所が絞られています。

細かい配慮：
- ログインIDが存在しない場合とパスワード誤りを**同じ応答**（`401 INVALID_CREDENTIALS`）にし、IDの存在を推測させない
- 他人のお知らせを既読にしようとすると `404`（存在を教えない）
- `production` で `JWT_SECRET` 未設定なら**起動時に例外**を投げる
- 公開プロフィールから **却下・審査中の依頼と平均報酬を出さない**（却下件数が見えると「危険な依頼を出した人」と特定でき名誉に関わる／平均報酬は値下げ圧力になる）
- ワーカー本人にも**評価者は伏せる**

### Q7-4. インフラ側の対策は？

**回答**

| 対策 | 内容 |
|---|---|
| デプロイ認証 | **Workload Identity 連携**。サービスアカウント鍵を GitHub に置かず OIDC で検証。**流出して困る長期鍵が存在しない**。`assertion.repository=='Syooosuke/AI-HACK-2026'` の条件付き |
| Maps APIキー | **ブラウザ用とサーバー用を分離**。ブラウザ用はリファラ制限＋API絞り込み、サーバー用（Street View Static）はIP制限 |
| 課金の暴走防止 | Geocoding/Places/Street View 各1,000/日、Maps JS 3,000/日の上限。Cloud Run max-instances backend 3 / frontend 5。予算アラート $10 |
| フロントの再試行 | GET / HEAD の通信例外のみ1回再試行。**POST / DELETE は再試行しない**（二重受注・二重依頼という実害が出るため） |
| 受注の競合 | `SELECT ... FOR UPDATE` でタスクをロックし、有効枠を数えてから作成。超過は `409 TASK_FULL` |

**キーがブラウザに露出する点は隠しません。** `NEXT_PUBLIC_*` はJSに焼き込まれるので原理的に
隠せません。リファラー制限・APIの絞り込み・1日上限が防御線です。

### Q7-5. セキュリティで足りていない点は？（自分から出す）

**回答**
以下は認識したうえで未実装です。

- **APIのレートリミットが無い**。総当たりログインや大量投稿を止められない
- **JWTの失効リストが無い**。有効期間30日で、ログアウトはクライアント側のトークン破棄のみ
- **位置偽装は完全には防げない**（Q5-7）。モバイルWebのため端末証明（Play Integrity / App Attest）が使えない
- **生成AIで作られた偽画像の検知は未実装**
- 監査ログのアクセス制御・保持期間ポリシー（Q7-2）

## 8. 次世代性・独創性

### Q8-1. 「次世代」と言える点はどこですか？

**回答**
生成AIを会話や文章生成ではなく、**業務の合否判定そのもの**に置いたことです。
このサービスでは、AIの判定が「参考情報」ではなく **依頼が公開されるか、報酬が支払われるか、
ワーカーの受注が取り消されるか** を実際に決めています。人間の目視検品は設計上どこにも
置いていません。

そのうえで、**AIの一回の回答をそのまま業務判断に使わないための構造**を作ったことが本題です。
決定論フィルタ、多数決、境界のみの再判定、Pydanticによる出力検証、位置・時刻の複合チェック、
スタブへのフォールバック——これらは全て「AIは間違える」という前提から設計されています。

### Q8-2. 独創的なのは技術ですか、組み合わせですか？

**回答**
**組み合わせです。** 個々の技術（VLM検品、YOLO、GPS検証）は新しくありません。独創性は、
**現地の人を探すマーケットプレイスと、依頼審査・画像検品・再撮影・プライバシー保護を行う
AIパイプラインを、一つのサービスとして接続した点**にあります。

さらに具体的に挙げるなら、**プライバシー保護を「撮影失敗」ではなく「納品前の必須工程」に
したこと**です。屋外撮影では通行人や表札が必ず写り込みます。多くのサービスはこれを
「撮り直してください」で処理しますが、私たちは検品プロンプトで
「**人物が写っていることを理由に減点・再撮影要求をしてはいけない**」と明示し、
合格後にマスキングして納品します。ワーカーの達成可能性と依頼者のプライバシー保護を
両立させるための設計判断です。

## 9. 技術選定の理由（一覧）

「なぜXを選んだのか」と個別に聞かれたときの答え。

| 選定 | 理由 | 採らなかった選択肢とその理由 |
|---|---|---|
| **FastAPI を別建て**（D-01） | YOLO / Pillow / OpenCV という Python の画像処理エコシステムが必要。`BackgroundTasks` で重い検品を非同期化しAPIは即 `202` を返す | Next.js の API Routes に統合 → 数GBのPyTorchを含む推論をフロントと同居させると、ビルド・スケール・デプロイ単位が全部引きずられる |
| **Next.js 14 App Router** | Server Component を既定にして状態を持つ画面だけ `"use client"`。カメラ（`getUserMedia`）とGPS（`watchPosition`）はブラウザAPIで足り、ネイティブアプリを作る必要がない | ネイティブアプリ → 9日間で iOS/Android 両対応は不可能 |
| **Supabase（PostgreSQL + Storage）** | DBとStorageが一体で、無料枠で足りる。ローカル開発と本番で同じStorage抽象を使える | Cloud SQL → 無料枠が無く月$10前後 |
| **Cloud Run** | **カメラと位置情報はHTTPSでないとブラウザが拒否する**。HTTPSのURLが自動で付き、リビジョン管理でロールバックでき、スケール0で待機コストがない | VM → HTTPS証明書とデプロイ経路を自分で作る必要がある |
| **OrcaRouter ＋ `OrcaClient` に集約** | 用途ごとのモデル差し替えが**環境変数だけ**でできる。業務ロジックにモデル名が漏れない | OpenAI/Anthropic SDK を直接 import → モデル変更が業務ロジックの変更になる。規約でも禁止している |
| **httpx で直接呼ぶ**（OpenAI SDKを使わない） | OpenAI Chat Completions 互換だが、`response_format` のスキーマ要件やルーターの振り分け挙動に固有の癖がある。薄く自前で持つ方が制御しやすい | OpenAI SDK → 抽象が一段挟まると 400 の原因が追いにくい |
| **ローカルYOLO**（D-09） | 原本画像を外部へ出さない／1枚あたりの外部課金ゼロ／レイテンシ | クラウドVision API → プライバシー保護処理のために原本を外部へ渡すことになり本末転倒 |
| **PostGIS を入れない** | バウンディングボックスのインデックスで粗く絞り、アプリ側の Haversine で正確な距離を出せば足りる | PostGIS → デモ規模のデータ量に対して依存と運用が重い |
| **決済はスタブ**（D-03） | 9日間でAIパイプラインの実装を優先。DBに記録だけ残す | 外部決済SDK → 実装・審査コストが期間に見合わない |
| **CPU版 PyTorch を明示的に先入れ** | ultralytics は既定でCUDA付き torch を引くが、Cloud RunはGPUを持たないため数GBが完全に無駄 | 既定のまま → イメージが肥大しビルドとコールドスタートが伸びる |
| **モデル割り当てを GitHub Variables に置く** | 秘密情報ではなく、「いつからどのモデルに切り替えたか」の履歴が事故調査で効く | Secrets → 変更履歴が追えない |

## 10. 現実装の限界（自分から言うリスト）

**聞かれる前に1つ2つ自分から出す。** 全部言う必要はないが、突かれたら即答できるようにしておく。

### AI判定の限界
- **位置偽装を完全には防げない。** GPS座標は端末の申告値。多層チェックで偽装コストを上げているだけ
- **C-5 の日出没判定が簡易**（6時〜18時を daylight）。季節と緯度を考慮していない
- **ベンチのサンプル数が小さい**（依頼審査22件、画像検品5〜9ケース）。統計的な精度保証ではなく、**回帰を検知するための固定セット**という位置づけ
- **検品は合格側に倒す設計**。対象の有無（`subject_present`）は緩めていないが、粗い写真は通す
- **AI判定への異議申し立てフローが無い。** 誤却下・誤失格を人が覆す手段が実装されていない
- **生成AIで作られた偽画像を検知できない**

### アーキテクチャの限界
- **検品が `BackgroundTasks` で走る。** 専用のジョブキューではないため、Cloud Run のインスタンスが
  リクエスト応答後にCPUを絞られる／スケールインで落ちると、処理が中断しうる。
  実測30秒〜15分かかる処理をこの方式で回しているのは**期間内の割り切り**であり、
  本番運用なら Cloud Tasks / Pub/Sub などのキューへ出すべき箇所
- **APScheduler がインスタンスごとに動く。** backend の max-instances は3のため、
  期限クローズジョブが複数インスタンスで同時に走りうる。ジョブはステータス条件で対象を絞るため
  大きな破綻はしないが、**通知の重複が起きうる**。分散ロックは入れていない
- **孤児ファイルを許容**。検品失敗時に Storage 上の原本が残る（削除処理は未実装）
- **レートリミット無し**、**JWT失効リスト無し**

### 未確認・未実装
- **OrcaRouter の画像生成APIの正式な形式が未確認。** OpenAI images 互換を想定して実装し、
  `ORCA_ROUTER_IMAGE` 未設定ならストリートビュー画像へフォールバックする
- **決済がスタブ**（D-03）。収益化の実証はゼロ
- **`reality_score` の減点幅（−40 / −25 / −20 / −5）に統計的根拠は無い。** 設計者の重み付け

## 11. ビジネス的な良さと問題（まとめ）

### 良さ

| 観点 | 内容 |
|---|---|
| **原価構造** | 検品の人件費がほぼゼロ。人力検品では粗利が消える**低単価・小口の依頼**が成立する |
| **供給の獲得コスト** | ワーカーは通勤・買い物のついでに1枚撮るだけ。専門スキル・機材・研修が不要 |
| **キャッシュの回転** | ワーカー単位で逐次検品・逐次納品・逐次報酬確定（D-07）。N人依頼でも全員完了を待たない |
| **スケールの形** | 依頼件数が増えても検品コストが線形の人件費にならない（LLM従量課金にはなる） |
| **横展開** | 不動産管理、屋外広告の掲出監査、工事進捗、保険の現況確認、災害後の状況確認。**いずれも今は人が現地へ行っている** |
| **蓄積される資産** | プロンプト・しきい値・ベンチの固定セット・失敗事例。ベンチには「暗い/手ブレ/傾き/遠い」など**合格すべき粗い写真**が6ケース入っており、これ自体がノウハウ |

### 問題

| 観点 | 内容 |
|---|---|
| **二面市場のコールドスタート** | 依頼地点にワーカーがいなければ成立しない。地理的密度が命で、全国同時展開はできない |
| **単価レンジの狭さ** | ワーカーが移動する動機が出る額と、依頼者が払える額の間が狭い。実データ未検証 |
| **法務の責任分界** | 撮影の適法性（私有地・肖像権・施設管理権）で問題が起きたとき、AIが承認した依頼の責任所在が未定義。利用規約と保険が無い |
| **労務** | ワーカーの業務委託性。反復的に稼働した場合の労働者性の議論 |
| **AI誤判定の事業コスト** | 誤却下＝依頼者の失注、誤失格＝ワーカーの離脱。**異議申し立てフローが無い** |
| **品質保証の下限** | 合格ラインをAIが決める。依頼者が「これでは足りない」と言ったときの再依頼・返金ポリシーが無い |
| **変動費としてのLLMコスト** | 1依頼あたり8〜14回の推論。低単価依頼では粗利を直接圧迫し、モデル選定＝ユニットエコノミクス |
| **模倣可能性** | AI機能自体は競合が後付けできる。堀はマッチング密度とチューニング資産の側にある |
| **決済未実装** | 収益化の実証がゼロ（D-03） |

## 12. 答えにくい質問への備え

### Q. 結局デモはスタブで動かしているのでは？
実モデルで動作します。Phase 3〜5 で `OrcaClient` の実HTTP実装、実VLM検品、実YOLOマスキングを
すべて完了させ、実測ベンチ（`bench_models` / `bench_task_review`）も実課金で流しています。
スタブは**当日の外部API障害への保険**として維持しているもので、当日の設定は
`ORCA_STUB_MODE` の値で切り替わります。どちらで動かしているかは即答できます。

### Q. AIが人を失格にする（受注を取り消す）のは危険では？
その懸念は共有しています。だからこそ**再撮影を2回まで認め**、検品プロンプトに
「判断できるのに不合格にする損失は、多少粗い写真を合格にする損失よりはるかに大きい」と明記し、
配点も対象の有無へ寄せました。加えて、**AI呼び出しが失敗した場合（`error`）は
`retake_count` を増やしません**——ワーカーの責任ではないからです。
一方で、**誤判定に対する異議申し立ての導線が無いのは現時点の欠落**で、
実運用に出す前に必要だと認識しています。

### Q. 9日間で本当にこれを作ったのですか？
デモ優先（D-10）でフェーズを切りました。Phase 2 で**AIをスタブのまま画面①〜⑩を一気通貫で
成立させ**、そこからAI機能を1つずつ実物に差し替えています。この順序のおかげで、外部AI APIの
仕様が未確定な間も全体の開発が止まりませんでした。フェーズ構成と各フェーズの完了条件は
`docs/06-phases.md` に残っています。

### Q. ドキュメントが立派すぎませんか。実装と合っていますか？
`docs/02-database.md` は `backend/app/models/` と1対1で対応しており、
`docs/06-phases.md` には**取り下げた完了条件も理由付きで残しています**
（例：「暗い画像・ブレた画像が不合格になる」は、まともな写真が再撮影になっていたため取り下げた）。
テスト294件が仕様の機械的な検証になっています。

### Q. 誰も使わないのでは？
現時点でユーザーはいません。実証していないのはそのとおりです。ただし、**代替手段が
「自分で行く」か「人を派遣する」しかない業務**（不動産の空室確認、広告の掲出監査、工事進捗）が
既にコストを払って存在していることが、需要側の根拠です。次にやるべきは、
その1業種に絞ったパイロットで実際の単価と成約率を取ることだと考えています。

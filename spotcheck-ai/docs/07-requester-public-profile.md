# 07. 依頼者の公開プロフィール（設計）

> `CLAUDE.md` 3節「仕様書に記載のない画面・機能を追加したくなったとき」に該当するため、
> 設計時点で人間の承認を得ている（8節に決定事項）。
> **実装完了後、この内容を `docs/03-api.md` と `docs/05-frontend.md` へ反映し、本ファイルは削除する。**

## 1. 目的

ワーカーが**受注する前に「誰の依頼か」を確認できる**ようにする。

現状、ワーカーは依頼内容しか見えず、依頼者が信頼できるかを判断できない。
一方でクライアントは画面⑩でワーカーの評価（信頼度スコア・星）を見られる。
**この非対称を解消する**のが狙い。

- ワーカー: 実績のある依頼者かを見て受注を判断できる
- クライアント: 実績が可視化されるため、依頼の質を保つ動機になる

## 2. 画面設計

### 2.1 新規画面: 公開プロフィール `/users/[userId]`

**閲覧専用。編集機能は持たない。** 自分自身のIDを開いても同じ表示（編集は既存のマイページで行う）。

| セクション | 内容 |
|---|---|
| ヘッダー | アバター / 表示名 / 利用開始月（例「2026年8月から利用」） |
| 依頼者としての実績 | 公開した依頼数 / 完了した依頼数 / 完了率 |
| ワーカーとしての実績 | 信頼度（5段階の星）/ 合格した提出数 |

**平均報酬は公開しない**（8節の決定）。依頼者にとって相場を見られる不利があり、
値下げ圧力や相場の固定化につながるため。完了率と依頼件数でワーカーの判断材料としては足りる。
| 空状態 | 実績が0件の側は「まだ実績がありません」と表示し、セクション自体は出す |

- 実績が両方0でもページは成立する（新規ユーザー）
- **ロールに依存しない**。1人が依頼者とワーカーの両面を持ちうる前提で作る（4節参照）

### 2.2 導線: 画面⑤ 依頼詳細・受注 `/worker/tasks/[taskId]`

「撮影条件」の下に**依頼者の行**を追加し、タップで `/users/[clientId]` へ遷移する。

```
┌────────────────────────────┐
│ 依頼者                      │
│ 👤 デモ株式会社        ›    │  ← タップで公開プロフィールへ
│    完了率 75%・依頼12件      │
└────────────────────────────┘
```

行の中に要約（完了率・依頼数）を出しておくと、遷移せずに判断できるケースが増える。

### 2.3 導線を置かない画面

| 画面 | 理由 |
|---|---|
| 画面③（クライアントの依頼詳細） | 自分の依頼なので不要 |
| 画面④（依頼一覧・地図） | 1カードの情報量が増えすぎる。まず⑤で運用して必要性を見る |
| 画面⑨⑩（結果閲覧） | 既にワーカー評価があり、依頼者は自分自身 |

## 3. API設計

### 3.1 `GET /api/users/{userId}/public`

認証必須（`X-Demo-User-Id`）。ロールの制約なし（誰でも誰でも見られる）。

**レスポンス `200`**

```json
{
  "id": "11111111-1111-1111-1111-111111111111",
  "displayName": "デモ株式会社",
  "avatarUrl": null,
  "joinedAt": "2026-08-01T00:00:00+09:00",
  "asRequester": {
    "publishedTaskCount": 12,
    "completedTaskCount": 9,
    "completionRate": 0.75
  },
  "asWorker": {
    "trustScore": 4.6,
    "approvedSubmissionCount": 8
  }
}
```

- `404 NOT_FOUND`: 存在しないユーザー
- `trustScore` は既存仕様どおり5段階へ換算（`trust_score / 20`、小数第1位）

### 3.2 公開してよい情報 / 出さない情報

**出さない**（意図的に除外する）

| 項目 | 理由 |
|---|---|
| `email` / `login_id` | 個人情報・認証情報 |
| **却下された依頼（`rejected`）** | 「危険な依頼を出した人」と特定でき、名誉に関わる |
| 審査中・情報補足待ち（`screening` / `needs_info`） | 未公開の下書き相当 |
| 依頼の位置情報・本文 | 個別の依頼詳細で足りる。プロフィールで束ねると行動追跡に使える |
| 決済情報 | D-03のとおり記録のみで、表示対象外 |

**統計の母数**: 一度でも公開された依頼のみ、すなわち
`status IN ('open','in_progress','completed','expired','cancelled')`。
`completionRate = completed / 母数`（母数0なら `null`）。

### 3.3 `GET /api/tasks/{taskId}` への追加

画面⑤で依頼者名を出し、リンクを張るために依頼者の要約を含める。

```json
"requester": {
  "id": "uuid",
  "displayName": "デモ株式会社",
  "avatarUrl": null,
  "publishedTaskCount": 12,
  "completionRate": 0.75
}
```

- クライアント自身が見た場合も同じ形（自分の情報が入るだけ）で、出し分けはしない
- N+1を避けるため、集計は1クエリでまとめて取得する

### 3.4 データモデルへの影響

**マイグレーションは不要。** 既存の列で計算できる。

| 出したい値 | 算出元 |
|---|---|
| `publishedTaskCount` / `completedTaskCount` | `tasks.client_id` + `tasks.status` |
| `trustScore` | `users.trust_score` |
| `approvedSubmissionCount` | `users.completed_task_count`（合格時に加算済み） |
| `joinedAt` | `users.created_at` |

将来アクセスが増えたら集計をキャッシュする余地はあるが、デモ規模では都度集計で足りる。

## 4. 並行して進んでいる作業との整合

同時に3つのワークツリーが動いている。**この設計は次の2つと衝突しないことを前提に置く。**

| ブランチ | 内容 | この設計への影響 |
|---|---|---|
| `feat/auth-and-unified-nav` | **`users.role` を廃止**し、1アカウントで依頼・撮影の両方を行う。`login_id` / `password_hash` を追加 | URLを `/users/[userId]` とし、`role` に依存しない構造にする。依頼者・ワーカー両面を1ページに出すのは**この方針に合わせたもの** |
| `feat/avatar-and-trust-gauge` | アバターと信頼度ゲージ | **表示コンポーネントは新規に作らず、あちらのものを使う。** マージ順で衝突しないよう、このブランチではコンポーネントを追加しない |

- `role` を参照するコードを増やさない（廃止予定のため）
- アバター表示・星/ゲージ表示は既存または `avatar-trust-gauge` 側の実装に寄せる

## 6. テスト計画

| 観点 | テスト |
|---|---|
| 公開範囲 | レスポンスに `email` / `login_id` が**含まれない**ことを機械的に検証 |
| 却下依頼の非公開 | `rejected` / `screening` / `needs_info` の依頼が統計の母数に入らない |
| 完了率 | 母数0なら `null`、`completed / 母数` が正しい |
| 認可 | 未認証は 401。存在しないユーザーは 404 |
| 両面表示 | 依頼実績のみ / ワーカー実績のみ / 両方 / 両方0 の4パターン |
| 画面⑤ | 依頼者行が表示され、リンク先が `/users/{clientId}` になっている |

## 7. 未確定・将来の検討事項

- **統計のキャッシュ**: 依頼数が増えたら都度集計をやめて集計列やビューに寄せる。デモ規模では不要。
- **「公開した依頼」の判定**: 現在の `status` から近似している。`cancelled` は一度公開された前提で
  母数に含めるが、公開前に取り消した依頼（`screening` → `cancelled`）は区別できない。
  厳密にするなら状態遷移の履歴テーブルが必要で、今回は入れない。
- **画面④への導線**: まず画面⑤だけで運用し、必要性が見えたら広げる。

## 8. 決定事項（2026-08-11 / 人間の承認済み）

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| 1 | 平均報酬の公開 | **公開しない** | 依頼者にとって相場を見られる不利がある。値下げ圧力・相場の固定化を招く |
| 2 | 却下依頼の扱い | **統計の母数から除外** | 却下件数が見えると「危険な依頼を出した人」と特定でき名誉に関わる。審査中・情報補足待ちも未公開の下書き相当として除外 |
| 3 | 導線の範囲 | **画面⑤ 依頼詳細のみ** | 受注を判断する画面に置く。一覧カードは情報量が増えるため見送り |
| 4 | ワーカー側の公開 | **同じURLで両面を出す** | `/users/[userId]` 1本で依頼者・ワーカー両方の実績を表示。`role` を廃止する `feat/auth-and-unified-nav` の方針と整合する |
